What it does

A single admin screen that lists the Store applications with an available update, lets the admin select any number of them, launches the installs, and tracks them to completion — including unattended runs where the browser is closed. Installs use the logged-in admin's session (no stored credentials); a server-side job monitors and finalises each install.

Architecture

  • UI Page pgi_plugin_updater — a Jelly body fragment (no <!DOCTYPE>/<html>) with design-token CSS scoped under #app and a vanilla-JS IIFE. Views: Home · Wizard 1–3 · Monitor · Guide. No framework, no bundler.
  • Script Include PluginUpdaterAjax (client_callable, extends AbstractAjaxProcessor, ES5). Methods return JSON strings consumed via GlideAjax.getXMLAnswer: getInstanceInfo, getUpdatableApps, createBatch, attachWorker, failRow, getBatchStatus, getMyLatestBatch, listBatches, monitorBatches, getProgress, verifyVersion, logInstall.
  • Table u_plugin_updater_install_log — install history; a batch is a group of rows sharing u_session_id. CRUD restricted to admin.
  • Scheduled Job Plugin Updater - Monitor Batches (every 1 min) — polls sys_progress_worker, verifies the installed version, and finalises rows. Runs server-side, so installs complete and are tracked with the browser closed. Credential-free.

Install trigger (credential-free)

Each install is a client-side fetch to /api/sn_cicd/app_repo/install with X-UserToken: window.g_ck (the admin's own session). 400 “offering required” errors are retried automatically with the parsed offering id. No service account, no Base64, no loopback.

The CICD App Repo install API is single-flight (guarded by a “CICD Operation” mutex): concurrent enqueues return Error enqueueing app_install. The launcher therefore enqueues installs sequentially and retries transient enqueue/mutex collisions with backoff — the installs themselves still run concurrently server-side once enqueued.

Unattended batch & monitoring

On launch the client creates the batch (one queued row per app) and fires all triggers in waves of 6 within seconds; then it can be closed. The Monitor page reads batch state from the server, polls every 15s, and on reopen reloads the user's most recent batch automatically (a batch selector lists recent ones). Columns are sortable.

Constraints honoured

  • OK No React, no bundler, no Fluent — single no-build UI Page rendered as a Jelly fragment.
  • OK No stored credentials, no Base64 — installs use the admin session token.
  • OK One data path — all reads via a single client-callable Script Include (GlideAjax). No REST Table API fallback for reads.
  • OK ES5 server-side; version label from glide.buildtag/glide.buildname (not glide.war).
  • OK All user-facing text in English; global scope; one portable Update Set.

Key decisions & lessons learned

  • UI Page must be a Jelly body fragment. Emitting a full <!DOCTYPE html> document inside Jelly collides with this instance's Next Experience shell (module-redefinition errors → blank page). The fragment renders correctly inside the platform frame.
  • No CDATA / no reserved words. ServiceNow's Jelly tolerates raw </&& in <script>; a CDATA wrapper broke parsing. (Also: if is a reserved word — never a variable name.)
  • GlideAjax response pattern. Methods must return JSON.stringify(...) (read by getXMLAnswer), not newItem().setAttribute('answer',…). Client params are passed with the sysparm_ prefix.
  • No duplicate Script Includes. A second class with the same name shadows yours and returns empty — keep exactly one.
  • Count aligned to Application Manager (231) via update_available ^ active ^ hide_on_ui=false ^ install_date≠empty.
  • Unattended = client-fires-all + server-monitors (credential-free), chosen over a server-side trigger that would have required a stored service-account credential.

Caveats

  • Note The 231 list matches the native Application Manager and therefore includes some platform-bundled apps that cannot install via the Store REST API — these are marked Failed with a message (same behaviour as the native flow).
  • Note The browser tab must stay open during launch (sequential enqueue, a few seconds for small batches, longer for large ones or under CICD contention). After launch, installs and monitoring continue server-side; closing/reopening is safe.
  • Note JARVIS/AI-generated output — review before use beyond a dev instance.

Deployment

  1. Open the completed Update Set record and use Related Links → Export to XML to download Now Plugin Updater.xml (see Update-Sets/README.md; the export_update_set.do endpoint is not available on these instances).
  2. On the target: Retrieved Update Sets → Import Update Set from XML → Preview → Commit.
  3. Open pgi_plugin_updater.do as an admin.
